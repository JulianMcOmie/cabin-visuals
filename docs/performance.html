Cabin Visuals — Rendering Performance

How the visual engine turns a beat into pixels, where the per-frame work goes, and what governs it. All paths are under src/editor/. Numbers are from the probes in scripts/perf/ on real saved projects (2026‑08‑18).

1. The one rule that makes performance tractable

Every visual is a pure function of the current beat (plus the document and params). Nothing in an instrument reads a clock, a delta, or a random number. This means: a paused frame is a frozen frame that need not be re-rendered; scrubbing shows exactly what playback shows; and export just steps the beat arithmetically through the same path. Almost every optimization below is “don’t do the work again when the beat and inputs didn’t change.”

3. Paused = idle: the render governor

While paused, the r3f canvas runs frameloop="demand": nothing renders until something asks. The governor asks for exactly one frame when an input changes — a store edit (params reach the engine synchronously), the debounced re-resolve, a scrub, or a resize. While playing the loop is 'always'. Export pins 'never' and steps frames itself.

src/editor/components/visual/RenderGovernor.tsx 
useProjectStore.subscribe(() => invalidate())            // any edit → one frame
subscribeObjects(() => invalidate())                     // re-resolve landed → one frame
useTimeStore.subscribe((s, prev) => {
  if (!s.isPlaying && (s.currentBeat !== prev.currentBeat || prev.isPlaying)) invalidate()
})

Measured on a real project, paused: 0 GL frames, 0 bleed copies per 3 s, ~88 % idle. Every other loop follows the same contract: the ambient-bleed painter parks 300 ms after the last change; library vignettes pause offscreen; the timeline glow sweep early-exits once cleared.

6. How the GPU is used

Everything on screen is one WebGL2 context, driven by three.js through react-three-fiber. There is no compute, no WebGPU; “GPU utilization” is a handful of explicit decisions:

Resolution. The canvas renders at dpr={1} with antialias: false — every scene rasterizes into 1× (CSS-pixel) offscreen targets and only the final grade quad touches the default framebuffer, so a HiDPI/MSAA backbuffer would just upscale a 1× image. This is also exactly what export renders.

src/editor/App.tsx 
<Canvas frameloop={isPlaying ? 'always' : 'demand'} dpr={1} gl={{ antialias: false }} shadows="soft">

Preview quality (a flag). Every offscreen target is sized by one scale: Final = 1, Auto = 0.5 while playing / 1 while paused, Fast = 0.5, Fastest = 0.25. Export pins 1.

src/editor/store/UIStore.ts · components/visual/useRenderTargetScale.ts 
export const PREVIEW_QUALITY_SCALE = { final: 1, auto: 0.5, fast: 0.5, fastest: 0.25 }
return exportPinned ? 1 : previewQualityScale(previewQuality, isPlaying)

Batching. Splitter copies of the 3D Shape family draw as ONE InstancedMesh2 per track (matrices, colors and opacity live in GPU textures) instead of one mesh per copy. Other instruments mount one mesh per copy.

No compiles during play. Every pass’s programs are compiled in-frame with the pass’s render state right after mount (and once after lazy instrument chunks settle), so nothing links a shader on the first beat.

Uploads. Canvas-backed instruments upload textures only when their canvas changed (Midi Roll ≈ 2 MB per changed frame at 576×1024; Text Display words are shared textures, prewarmed). Photos decode off-thread before their first upload.

The 2D-canvas readback trap. Chrome only GPU-accelerates a 2D canvas above ~16.5 k pixels. The ambient bleed copies the WebGL canvas into a small 2D canvas 15×/s; at 128×72 that canvas was CPU-backed and each copy was a full framebuffer readback. It is now 192×108, so the copy stays on the GPU.

7. What outside the engine can still slow playback

  • Timeline blocks. The glow is a CSS filter driven by a variable the playhead RAF rewrites; blocks get a compositor layer (will-change) only while the transport runs. Without it, ~10 % fewer frames with 138 blocks visible (measured headed, real GPU). Files: components/timeline/Block.tsx, midiActivityRegistry.ts.
  • Forced layout. Nothing in a per-frame path may read layout (scrollLeft, getBoundingClientRect) after styles were dirtied; the playhead reads mirrored values instead. One such read cost ~40 % of playback JS on an 11 k-note project.
  • Session replay. PostHog recording is paused on /editor (rrweb’s mutation observer and canvas capture were ~half the main thread during play). “Record canvas” must also be off in the PostHog project settings.
