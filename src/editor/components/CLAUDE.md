# src/editor/components — the editor UI

Three big surfaces plus the inspector. **The timeline and the piano roll have separate gesture systems on purpose** — don't try to unify them.

## The render budget (load-bearing)

Timeline gestures write ProjectStore on **every pointermove**, so per-edit React work
must stay O(one row), not O(project). Measured before this contract existed: ~450ms
of JS per single `updateBlock` at 30 dense tracks — the entire editor re-rendered per
move. Two rules keep it fixed:

1. **No whole-record subscriptions in always-mounted components.** `s.tracks` and
   `s.scenes` change identity on every edit (so does `s.scenes[activeSceneId]`).
   Subscribe to primitives, per-id slices (`s.tracks[id]` keeps its reference when
   other tracks change), string-valued derived selectors, or a string fingerprint +
   `getState()` in a `useMemo` (see SceneTabs, MoverTargets). `TimelineArea` is the
   one legitimate whole-`tracks` subscriber — it maps the rows. (The color
   resolvers in `utils/trackDisplayColor.ts` are pure functions of the track now —
   no subscription needed at all.)
2. **`Track`, `Block`, `NotePreview`, `AudioBlock` are `memo()`d, and every prop they
   take must be referentially stable across foreign edits.** The traps that would
   silently undo it: inline closures in TimelineArea's row map, per-render arrays
   (`previewRowPitches`, `guides` — both flow into `Block`'s activity-registry effect
   deps, so instability also re-registers every block per move), and the palette
   object in `Block`. Two whole-stack sweeps were measured and fixed 2026-08-19:
   rows do NOT take `timelineWidthPx` (the lane is `flex-1` in the row, so the
   project auto-growing under a drag is a CSS reflow, not a re-render of every
   row), and `Track`'s comparator (`trackPropsEqual`) treats `selectedBlockIds`
   as equal when membership over the row's OWN blocks is unchanged - the Set's
   identity legitimately changes on every selection write, and by identity one
   click re-rendered all rows. A NEW prop must come with a stability story; `npx eslint` won't
   catch it, a re-measure will (workspace CLAUDE.md has the MessageChannel probe;
   steady state ≈11ms/edit at 30 dense tracks in dev — regressions read as a jump
   back toward hundreds).

Known accepted staleness from rule 1: a mover lane's *timeline preview* row order
(prior-copy-count) and the roll's declared rows refresh when their own track next
changes, not on sibling chain edits — cosmetic, and the full editor re-resolves on
open. The debounced structural resolve (`VisualBeatSync.setProject`) reuses
per-track resolutions by identity (see core/visual/CLAUDE.md), so a one-note edit
re-resolves one track, not the scene.

## timeline/ — the arrangement view

- `TimelineArea.tsx` orchestrates: ruler, playhead (`usePlayhead` writes px via RAF, no re-render per frame), scrub, loop-region drag, track rows.
- `trackTree.ts` flattens the track forest into visible rows (collapse-aware); `Track.tsx` renders a row (label strip + lane); `Block.tsx`/`AudioBlock.tsx` the blocks.
- Gestures: `useTrackGestures` (block move/resize/draw), `useTrackNestDrag` (reparenting, drop indicators via `trackDrop.ts`), `useTrackCopyDrag` (alt-drag duplicate). Child-lane rules: envelope/ability lanes never re-parent by plain drag but alt-drag COPIES them onto any parent; AUTOMATION lanes both move and copy between parents — landing under a parent that can't take the lane's target calls the store's `remapAutomationTarget` with the caller-resolved option list (`utils/automationTargets.ts` — the store can't read instrument defs), which defaults the target and remembers the displaced one so dragging back restores it. All three lane types are barred from ROOT drops (they live only on a parent). Sibling drops land on ROW BOUNDARIES, and one boundary can mean several nesting depths (after a grandchild: its sibling, an uncle, a root track — same line): `computeDropTarget` picks the depth from the pointer's X, one `INDENT_PX` step per level, clamped to the boundary's valid range and falling back shallower past parents that can't nest or are being dragged. Any level is reachable, arbitrarily deep; the middle band still nest-appends into the hovered row. (`utils/edgeResize.ts` is the LABEL-COLUMN gutter drag, shared with the piano roll — not block edges.)
- **Every horizontal line in the label column starts at `rowIndentPx(depth)`** (trackDrop.ts) — the row's PARENT bracket, i.e. `LABEL_BASE_PX + (depth-1)*INDENT_PX`, NOT `depth * INDENT_PX`. Row backgrounds, the divider below a row (which uses the *next* row's value), and both drop indicators all share it, so an indicator previews the exact line it will become; the raw indent step is 4px off at every depth. The outline also **bends**: a parent's bottom line turns the corner at its child bracket (`BRACKET_CORNER_RADIUS_PX`) and runs down beside its children, so the nest-into highlight drops its straight bottom border for the two bend spans in `Track.tsx` — the highlight's FILL always wrapped the children (the strip inherits it), and a straight border cut across it. Those spans are painted over the children's own chrome, which is why the highlighted label goes `z-[25]`: all rows sit at z-20, so later siblings (its children) otherwise win.
  **The INSERTION LINE, though, is always straight** — the divider it replaces may be a bracket corner, but a bending indicator reads as a hook hanging off the row above, and the nest-into highlight for the same landing is a plain box, so the two indicators for one drop disagreed. `line` carries no bend flag at all (the `curve` field was removed 2026-08-15); `RowGuide.curve`, the real first-child corner in `Track.tsx`, is a different thing and stays.
  **Otherwise an indicator previews chrome that EXISTS, and only the drop's own row may repaint it.** Two corollaries, both of which shipped wrong once (fixed 2026-08-15):
  (i) A nested row's own deepest guide sits at exactly `regionLeft` — **the same pixel as the nest-into outline's left border, and painted after it** (guides come after the background div in the label's DOM, and paint order here is DOM order; they cannot move earlier because the opaque background would cover them). So the blue left edge was invisible on every nested target and correct only on root rows. The guide wears `var(--accent)` while `dropInto` instead of being suppressed — same geometry, first-child corner included, in the outline's colour.
  (ii) **The nest-drag's source row is a placeholder, not a faded row**: `opacity` on the row wrapper fades the label chrome too, so the ancestor bracket lines broke for exactly that row's height, and the row's now-translucent background let the lane surface through while the parent's opaque strip in the indent gap beside it did not — a left margin appearing mid-drag. `dimmed` fades only the CONTENT (name block, control cluster, the lane's block wrapper) via `ghostOpacity`.
- **Edge grab zones are SCREEN space, their targets are content space** — the mismatch is the whole trap. A block's resize/loop handles and the ruler loop band's insets are CSS px (`getBoundingClientRect`/`clientX`; timeline zoom changes layout width, never a transform scale), but the block or band they sit on shrinks as `tracksPixelsPerBeat` drops toward its floor of 2. Every such zone goes through `edgeHitPx(width, hit)` in `constants.ts`: the constant on-screen size, capped at 40% of the target so the middle always survives as a move zone. Do NOT re-introduce a bare `Math.min(HIT, w / 4)` — that quarter-cap made the handle collapse to ~2px at low zoom (a 1-bar block is 8px wide at ppb=2), which is what "the grab distance is too small when zoomed out" meant. Four call sites: `timeline/useTrackGestures.ts` (the gesture) and `timeline/Block.tsx` (the cursor/tooltip) must agree or the cursor advertises a handle the pointerdown won't honour; `midi/useMidiBlockGestures.ts` has its own pair for the clip header. In `Ruler.tsx` the cap also fixes a latent bug: two unclamped 10px insets on a narrow band overlap, and the later-painted `end` handle swallows the start edge and the move middle outright.
- **Block color voice** (`utils/colors.ts` `midiBlockPalette`, picked via the timeline color lab 2026-08-02): resting blocks are near-black panes with an inset hue hairline and lit neon notes (same L/C voice as the piano roll's notes); the selected/editing block is a "star anatomy" supernova — three-shell radial body (white heart → saturated corona), burning rim + five-layer bloom, **no selection ring of any kind**, and its notes flip DARK (outshone by the body, first-pass marks get a light-wrap glow, loop repeats dim by LOWER contrast). `Track.tsx` renders the selection's row-spill wash behind the lane's blocks; the cross-lane light is just the block's own box-shadow bloom bleeding over neighbor rows. `AudioBlock.tsx` speaks the same voice keyed on the audio sapphire: the waveform is its "notes" (lit ink resting, flipped dark + light-wrapped when the body ignites; the filename label flips dark with it), and the sync drag simply rides the selected state. Timeline chrome matches: `.timeline-glass-scope` (globals.css) drops `--bg-timeline` to near-black, labels to `#141415`, and swaps the bar gridlines to faint white via `--timeline-grid-line`; `.timeline-neon` (on TimelineArea's root, NOT the scope) dims the shared Ruler's numbers/lines/ticks via `--ruler-*` vars — kept off the scope because the piano roll's ruler is the same component inside the same scope, and its numbers sit over the hue-tinted clip-header band where the brighter defaults are needed. `core/visual/midiBlockPalette.test.ts` pins the inversions (dark pane / lit note, lit body / dark note, no ring). The STRUCTURAL hairlines (bar gridlines, row dividers, label edge, hierarchy brackets, ruler bottom) draw `--timeline-grid-line`/`--timeline-row-line` — OPAQUE pre-composited values, not alpha whites, because translucent lines SUM where they cross and every grid/divider corner rendered a brighter dot (and the brackets' overpaint-the-divider trick doubled instead of covering). Don't "simplify" them back to `--border`.
- **Every row wears an instrument mark** (`TrackIcon.tsx` + `trackGlyphs.tsx`, chosen from six candidate looks built into the live editor 2026-08-15): a 16px monotone glyph in `currentColor`, tinted with the track's display color re-voiced through `midiNoteBaseColor` — so the icon is *the same color as that row's blocks*, and a dim identity color can't make an unreadable mark. Deliberately NOT the library's card icons: those are multi-tone miniatures with no single color to replace, and thirty different hues in one column read as confetti. Color says which track, shape says which instrument. **A new instrument / mover / splitter / director needs a mark here** as well as its `LeftSidebar` card — `trackGlyph` falls back to a dashed circle, which ships as a visibly anonymous row rather than failing loudly. **Two instruments' marks are not fixed**: 3D Shape follows its geometry (`SOLIDS`, keyed by `FundamentalGeometryId`, so a new solid is a type error) and Wireframe follows its shape picker (`WIRE_SHAPES`, falling through to `SOLIDS` for the ten ids the two vocabularies share — a torus is a torus whichever draws it, and colour is what tells the rows apart). Wireframe stores an INDEX into an append-only list, so `wireframeShapeGlyph` resolves by **id** and clamps exactly as the instrument does; resolving by index would let a reorder silently repaint every row. `trackGlyphs.test.ts` pins all of it: every registered instrument/device/director has a non-fallback mark, and both shape vocabularies map to DISTINCT ones — that test is the real enforcement of the paragraph above. Keep marks distinguishable by SILHOUETTE at 15px, and watch for collisions across families: a torus drawn with a tight hole is an eye (the Visibility mover), and a Möbius drawn as a ring with a twist inside it is a torus — the crossing has to *be* the silhouette.
- **New CONTENT in a track label must be `position: relative`, or it renders under the row background.** The row-state surface, the bracket guides and the bottom divider are all absolutely positioned siblings declared FIRST in `Track.tsx`'s label; a positioned element paints above every non-positioned in-flow box regardless of DOM order, and that surface is opaque (`--bg-track-row`). So a plain static flex child still takes its width in the row and then paints *underneath* — a gap where the thing should be, which reads as the element failing to render rather than as a stacking bug (cost a round trip on the track-icon slot, 2026-08-15). The name group and the control cluster both carry `relative` for exactly this reason; anything added beside them owes it too.
- **The label column's surface and its divider against the lanes are VIEWPORT space**, one strip in TimelineArea's lane wrapper *outside* the scroll container — because the column itself is frozen (every row's label is `sticky left-0`). Painted in content space it slides away under horizontal scroll, which is invisible behind the rows (each row's own strip covers its label) but obvious in the empty space below the last track, where nothing else paints: the "track colors" there scroll while the tracks don't. Same reason the strip is full-height — it carries the label/lane divider past the last row to the bottom of the pane. Scroll room below the stack is the empty row's `minHeight`, NOT a `paddingBottom` on the content: padding is outside every flex child, so a background was the only thing that could reach it.
- **Empty scene** (`timeline/EmptySceneActions.tsx`, rendered by TimelineArea when `rootTrackIds` is empty): a list parked at the top of the lane region by bar 1, where every line is a BUTTON that does the thing it names — add a track ("Add a scene" on Main, matching what `insertTrack` actually creates there: a **Scene** composition track, which shows its scene with no notes drawn, rather than a Scene Switcher that renders nothing until played), import MIDI, load audio, start from a template. It replaced a sentence that narrated the `+` button and then taught right-click-to-draw-blocks, a gesture with no lane to perform it on yet; **that blocks lesson belongs to the empty TRACK, and still has no home** — if you build one, that is where it goes. Reuses the drop pipeline rather than forking it (`importMidiFiles` / `loadAudioTrack` / `showMediaNotice` from `MediaFileDropLayer`), via one hidden `<input type="file">` re-pointed per use. The wrapper is `pointer-events-none` with only the cluster `pointer-events-auto`, so scrub and loop drags still reach the lanes around it. No keyboard chips: nothing binds an add-track key, and a chip that lies is worse than none.
  **Motion** (`.empty-scene-*` in globals.css, chosen from a lab 2026-08-13): rows drift in from the LEFT, 105ms apart, `easeOutExpo` over 640ms — lateral so no row travels through where another will land, and the 105ms is what makes it read as four arrivals (under ~60ms they merge into one wave regardless of duration). Transform and opacity ride **different curves on purpose**: fading on a hard decelerate makes a row hit full brightness while still visibly moving, so it looks landed and then drifts — opacity is linear. The headline and all four rows must stay DIRECT children of the animated element (one `> *` rule staggers them via inline `--i`), which is why the headline wears `mb-` instead of the rows living in their own gap wrapper. **The component owns its own presence** (`empty` prop + an `EXIT_MS` timer) rather than being a `&&` in TimelineArea — a conditional render would rip it out with no chance to fade. Deliberately NOT `AnimatePresence`: framer-motion never completes when the tab is hidden, so it would hold the exiting child mounted forever (the documented Save-to-cloud bug); a timeout fires either way. TimelineArea keys it on `activeSceneId` so switching to another empty scene replays the entrance. `EXIT_MS` and the CSS duration must be changed together.
- **Reaching the library from elsewhere: `UIStore.libraryRequest` + `requestLibraryTab(tab)`.** The library's open/closed state is App-local (behind `togglePanel`'s glide + `suppressResizeUntilRef`) and its TAB is LeftSidebar-local, so a surface that wants "show me templates" cannot reach either. The request object is the bridge: App expands the pane (only when `isCollapsed()` — `togglePanel` FLIPS, so calling it on an open library closes it) and LeftSidebar sets its tab. Both consumers react to the object CHANGING, never to its presence, so neither clears it and there is no race over who clears first; the `nonce` is what makes a repeat request re-fire. Don't "tidy" this into a boolean-plus-clear.
- **Library drag onto an instrument row REPLACES it** (chosen from an interactive
  mock 2026-08-14): in `useLibraryDrag`, an instrument-kind card (anything that
  converts via `setTrackInstrument` on double-click — not mover/splitter/colorizer/
  formation) whose `computeDropTarget` resolves to the middle band of a `base`
  track becomes a `replace` target (`UIStore.trackDrop.replace`) instead of a
  nest; nesting stays reachable via the boundary line at a deeper indent, and
  mover-type cards still nest everywhere. The targeted row previews the FUTURE:
  `Track`'s `replacePreview` prop overrides the display color (name, blocks) with
  the post-swap identity — resolved from the track's wardrobe stash for that
  instrument, so a re-worn instrument previews in the color it will actually come
  back wearing — plus a row-wide wash/hairline (deliberately row-scoped, unlike
  the label-scoped nest-into wash). The drag ghost swaps its + for ⇄ "Replace X —".
  The ghost's `replaceOldName` is selected as a STRING so per-move trackDrop
  churn doesn't re-render the library.
- `TrackContextMenu.tsx` — add automation/ability/envelope/mover lanes, tags, etc. `TrackTagsPanel.tsx` (popup tag editor in the row), `TrackTransformPanel.tsx` (canonical `tf*` strip), `AudioTrackOscilloscope.tsx`, `midiActivityRegistry.ts` (per-track note-activity glow, imperative).
- **Row popovers (transform/tags panels) portal to document.body but their React events still bubble through the Track label** — and the label's nest-drag starter is `onPointerDownCapture`, which fires BEFORE any `stopPropagation` inside the panel can run (capture phase, ancestor first). So a panel cannot shield itself; the label's capture handler must skip portaled targets, which it does via `!e.currentTarget.contains(e.target)` (a React-tree child that isn't a DOM child came through a portal). A new popover mounted inside the label row is covered automatically; a new *capture-phase* handler on the row needs the same guard or dragging over the popover moves tracks again.
- Any continuous gesture that moves audio-affecting state must bracket with the transport's drag suppression (`beginBlockDrag`/`endBlockDrag` etc. — see core/playback.ts) or it recreates the "earrape" bug. The one AUDIBLE exception is the audio-block MOVE drag (`timeline/audioSyncDrag.ts`): it suppresses the per-move re-arm the same way but keeps playback sounding on a looped section, feeding fresh audio only through the loop wrap's seek and a debounced re-arm.
- **Pickup**: audio `startBar` may go NEGATIVE (audio leading bar 0). The pickup is *derived* — `utils/audioPickup.ts`, exactly `-min(startBar)` — never stored. Timeline content shifts right by `pickupPx` through exactly three seams: the per-lane block wrapper in `Track.tsx`, the ruler's `leadInPx` wrapper in `Ruler.tsx`, and `laneRef` in `TimelineArea.tsx` (which starts at MUSICAL beat 0, so every clientX→beat mapping derived from its rect — scrub, loop drag, track gestures — stays musical for free). Anything that maps content-x→beat *without* laneRef (e.g. `useLoopBlockDrag`) must subtract the pickup itself. The transport plays negative beats via a constant origin shift (bar 1024) inside `beatToPosition`/`positionToBeat` in core/playback.ts — Tone never sees a negative position.

## midi/ — the piano roll

- **The roll rides an exit animation, so it must outlive its own store state.** `BottomArea` (App.tsx) slides it away over the timeline when `editingBlock` clears — but `PianoRollPanel` reads `editingBlock` too, so the dismissing commit would empty the panel and what slides off screen is a black box. It takes a `frozenRef` (BottomArea latches the last ref) and, while the store is closed, falls back to the last track/block pair that rendered — which also covers dismissing BY DELETING the edited block, where the live lookup is legitimately gone. Anything new that early-returns on missing document state needs the same frozen fallback.
- `PianoRollPanel.tsx` hosts; `MidiEditor.tsx` is the canvas-based editor, reused for regular tracks, automation lanes (rows labelled by VALUE via the pitch encoding in `core/trackTypes.ts`), ability lanes, and pad-bank lanes (video/photo: one labelled row per pad).
- **Text tracks: the "Lyric clips" row is an ORDINARY note row** at `PITCH_LYRIC_CLIP`, unshifted by PianoRollPanel. A phrase is a note (see `src/editor/CLAUDE.md`), so the roll carries no clip gesture code at all — drawing, dragging, resizing, marquee, delete and undo are the note gestures, a phrase and the word notes it feeds can be boxed and moved as one because they live in the same array, and the phrase renders + retypes through the same `noteWords` / `onNoteWordEdit` channel a word note uses (`onNoteSelect` routes a clip note to the phrase sidecar instead of a style lane). ~150 lines of parallel clip machinery were deleted when this landed. **The one trap: the clip pitch must be withheld from `generateInstrumentRows`' unmapped-pitch rescue list.** No instrument declares that pitch, so the rescue builds a SECOND row for it beside the unshifted one — two rows sharing a pitch, which the row map keys by, giving duplicate-key warnings and clip notes drawn on whichever row won. Only the text roll withholds it; every other instrument keeps the rescue, or a stray note becomes unreachable.
- **The roll's vertical scroll is a chain of flex columns, and any wrapper that breaks the chain kills it silently.** `MidiEditor`'s grid scrolls via `flex-1 min-h-0 overflow-auto`, which only bounds a height inside a flex COLUMN whose own height is bounded — up through the side-rail row (`flex min-h-0 flex-1`) to `PianoRollContent`'s `flex flex-col h-full`. A plain-block wrapper anywhere in that chain lets the roll grow to its content height, so the grid never overflows, no scrollbar appears and the wheel does nothing (the rows past the pane are just clipped by the ancestor). Horizontal scroll keeps working — width is bounded by `min-w-0 flex-1` — so the symptom reads as "only vertical scroll is broken". Shipped that way once when the Text Display side rail added the wrapper.
- **Scroll room under the last row is a spacer sibling, not padding** (`CANVAS_BOTTOM_PADDING` in `MidiEditor.tsx`): the grid element is the rect every gesture measures against (`clientToGrid`), so growing IT would put pointer-reachable pixels past the last row. The spacer is `pointerEvents: 'none'` so a press there still reaches the scroll container's marquee handler, which only fires on `e.target === e.currentTarget`.
- `generateRows.ts` / `resolveDeclaredRows.ts` — which rows show: an instrument's `midiRows` vocabulary, else full piano. `coords.ts` — beat/pitch ⟷ px (the one place). **A vocabulary may resolve to ZERO rows** (e.g. a Scene Switcher with no scenes to bind — and note an empty `defRows` array is still truthy in PianoRollPanel's row ternary, so it never falls through to the full piano): the roll then swaps `MidiEditor` out for `EmptyRollBlank.tsx`, a deliberate blank state (ghost-rows sketch + copy), rather than mounting an empty scroller.
- Gestures: `useNoteGestures` (draw/move/resize/velocity; commits ONCE per gesture so undo gets one step), `useMidiBlockGestures` (the block's own bounds/loop from inside the editor). State: `useMidiEditorState`.
- **A note drag shows two things the timeline's block drag showed first**: the full-height alignment hairline (`[data-midi-note-drag-guide]`, placed imperatively by `placeDragGuideAtBeat` exactly like `useTrackGestures`' — it rides the grabbed note's snapped MOVING edge: left on move/left-resize, right on right-resize, the fixed start while drawing) and a hollow **drag ghost** at each dragged note's original footprint. Both are keyed off one non-obvious fact: **`setDragState` is only called per-pointermove for the MARQUEE** — a move/resize sets `dragState` once at pointerdown and then streams notes through `onNotesChange`, so `originalStartBeats`/`originalPitches`/`originalDurations` are frozen for the whole gesture and the ghost renders straight from them with no snapshot of its own. Anything that starts updating `dragState` during a move re-renders the ghost every frame for nothing (and note MidiEditor's lyric-clip group-drag effect already reads `dragState.currentX` while `'moving'`, which never advances — that path is suspect for the same reason). The ghost wears the note's own fill at reduced opacity — the same note left behind, not a differently-voiced marker.

### midi vim (`midi/vim/`) — the modal keyboard editor

A tracker grammar over the roll: a cursor with a size, modes (ground → `Tab` → select → `m`/`n` → a live move/copy draft), count prefixes, and operators on a region. Ported from the `VimAsMidi` prototype (`~/Desktop/Coding/VimAsMidi`, `src/lib/editorModel.ts`), whose *shape* — one pure reducer — is the reason it's testable; what changed is ownership. The port is now feature-complete against it apart from disjoint LOOP ranges (below); its `CURSOR_LENGTHS`/`cursorLengthIndex` are vestigial there too (`cursorLengthTicks` just returns the grid step), so there is no separate cursor-length concept to port. Off (the default), not one byte of roll behavior differs. `?` prints the whole map; `VimStatusLine` is the mode's real teaching surface.

- **The reducer owns no notes.** `vimReducer.ts` holds the cursor/mode/region/prefs and emits INTENTS; `useMidiVim` applies them through the roll's existing `commit()`, so an op is one store write hence one undo step, and HistoryStore needs to know nothing. The prototype's own notes array and undo stack were deliberately NOT ported. `newId` is injected through `VimContext` so the reducer stays deterministic under test (`vimReducer.test.ts`, in the normal `test:visual` suite).
- **The listener is on WINDOW in the CAPTURE phase, and that placement is load-bearing.** Capture runs outermost-first, so it beats `useNoteGestures`' *document*-capture handler and the transport's bubble-phase one without touching either — no registration-order coupling. Keys vim claims get `stopImmediatePropagation`; keys it doesn't (`handled: false` — every `⌘`-combo but `⌘`+note) are never touched, so ⌘C/⌘V/⌘Z behave identically. **Play/pause and return-to-start are recognised but deliberately passed through**, because App already binds Shift+Space and Enter; re-implementing them here would mean a second `usePlayback`, which re-inits the playback engine.
- **The region projects onto `selectedNoteIds`** (hence the setter now returned from `useNoteGestures`) rather than being a second selection concept — so the roll's selection visuals, ⌘C/⌘V and mouse drags all see what the keyboard region covers.
- **A cursor move seeks the transport when paused.** On a visual DAW the viewport IS the audition — this is the feature's whole reason for existing, and it falls out of the one rule (every visual is a pure function of the beat).
- **The note keys are Logic's musical-typing row** (`a w s e d f t g y h u j k o l p`), which is why navigation is on `z x c v` and the operators on the leftovers: those sixteen keys eat most of the alphabet. Three regimes in `keyMap.ts`, picked by the panel (`vimRegime`) because only it knows what the rows mean: `chromatic` (full piano, `a` = C of the octave), `vocabulary` (declared rows — positional from an anchor), and `value` (automation lanes, where pitch encodes a param value, so the sixteen keys spread across the WHOLE range — `a` min, `p` max, and typing a melody writes a curve). The row gutter draws each row's key while the mode is on; for an arbitrary vocabulary that's the only way the map can explain itself.
- **The PAGE is the coordinate system** (`VIM_PAGE_BARS`, four bars, rounded down from the cursor): `1-4` hop to its bars, `Shift+1-4` loop them, `Shift+z/x` travels a whole one, and `Shift+A` selects it. The grid draws a numbered strip over those four bars while the mode is live — without it the digits are an invisible coordinate system, which is exactly why they were dropped in the first pass and had to be put back.
- **Selections are disjoint on BOTH axes.** `VimSelection` carries `rowFilter` and `timeRanges`, each null meaning "whatever the anchor and cursor span" and each becoming an explicit set once you press a key — note keys build the rows, `1-4` build the bars. So "the kick and snare rows, in bars 1 and 3, skipping bar 2" is one region, and `r` travels it as a body. Toggling the last entry out of either set drops back to null rather than leaving an empty set that can never match.
- **Departures from the prototype, on purpose**: `[ ]` and `- =` write the roll's OWN quantize and zoom instead of shadow state, so the toolbar visibly moves as you press; `|` is a straight↔triplet TOGGLE (`VIM_TRIPLET_OF`) rather than another rung on the grid ladder; Escape pops exactly one level so panic-Esc always gets you out; `;` `'` jump note-to-note in TIME, a pair the prototype has no equivalent of (its `/` `?` column jumps live on `/` `\`, since `?` is the key sheet); and a count already under way swallows `1-4` (`52` works, `12` does not) where the prototype threw the count away and hopped — same one-key bar access, without discarding unambiguous intent.
- **`actionPendingClear`** is the prototype's subtlest idea and easy to delete by accident: after `r` the region stays selected and repeatable, so the NEXT nav key means "walk away from what I just made" and clears it instead of re-shaping it. That is what makes `r r r x` work with no Escape in between.
- **Shift+1-4 loops through `TimeStore.loopRegion`**, which is ONE contiguous span — the prototype looped a disjoint set (bars 1 and 3, skipping 2). Slots 1 and 3 therefore loop 1 *through* 3. Honouring it exactly would mean multi-range support in core/playback.
- Digits are read from `e.code` (`Digit1`/`Numpad1`), never `e.key`: `Shift+1` is `!` on a US layout and something else elsewhere, so the loop slots would be unreachable otherwise. The prototype resolves them the same way.
- **`midiVimEnabled` is session state in UIStore, not persisted** — a roll that silently opens with the keyboard claimed reads as a broken editor. Double-tap Shift (tracked in `useMidiVim`, and live even when the mode is off, since that's how it's turned on) or the toolbar's `⌶` chip re-arms it. Inside the mode a SINGLE shift tap latches chord staging, so a double tap is two latches — a harmless no-op.
- Typing past the block's end **grows the block** (`growBlockTo`, sorted ahead of the note write): the tracker flow is that you type until you stop and the clip follows. It costs a second undo step, which is the accepted trade.
- `SELECT` is in the typing-target guard alongside INPUT/TEXTAREA — vim stops claimed keys dead, so without it a note key at the open grid dropdown would write a note and never reach the dropdown.

## visual/ — the 3D viewport pipeline

- **Scene lighting is TRACKS** (2026-08-29): the hardcoded `lights()` rig in
  VisualScene only serves scenes with NO Light-instrument tracks (the fallback
  for hand-built fixtures); every seeded scene carries a "Lighting" group of
  Light tracks instead, mirrored into each pass by `MountedScene.lightPools`
  (one `PassLightPool` per base/front/invert scene, synced in the frame loop
  before the passes render - the BASE pool syncs unconditionally so deleted
  lights are removed, front/invert only when `passPresence` says the pass
  runs). ShaderWrapper's divergent hand-built rig now also stands down for
  track-lit scenes and mirrors the same registry, so effect-chained objects
  finally match their neighbors' lighting. See `core/visual/sceneLights.ts`
  and instruments/CLAUDE.md's Light section. `EmptySceneActions` treats a
  scene wearing only the Lighting group (and/or the scene track) as still
  empty, parked BELOW those rows via its `topOffset` prop.

- `VisualScene.tsx` — mounts one `ObjectRenderer` per `ObjectListEntry` from the engine (structural list; per-frame values are pulled imperatively). Renders scenes to render targets and composites the composition instruments' `CompositionLayer`s (partitions/flash/blur/bloom) into the final frame. Backdrop gradients are painted by `paintBackdropGradient` right after each backdrop clear (per-scene targets + the main composite) — a fullscreen no-depth pass, so filters/bloom/directors/export inherit them exactly like a flat clear color. The shader mixes stops in sRGB to match the panel's CSS previews pixel-for-pixel; keep it and `cssGradient` in SceneSettingsPanel in step.
- **Shift-hover / Shift+double-click in the visualizer** (`CanvasHoverPicker.tsx`, mounted
  inside the Canvas, 2026-09-04): hold Shift and move over the canvas to highlight every
  copy of the instrument under the pointer (a silhouette glow in the track's colour) and
  light its timeline row; Shift+double-click switches to its scene if needed, expands
  collapsed ancestors, selects it and scrolls the row into view (`UIStore.revealTrack`,
  consumed by TimelineArea). Objects live in offscreen portaled scenes, so r3f pointer
  events never see them: every occurrence root registers in
  `core/visual/hoverTargets.ts` (ObjectRenderer's placement group, InstancedObjectRenderer's
  wrapper group, ShaderWrapper's offscreen holder) and the picker raycasts those by hand
  after mapping the pointer through the composited layer it lands in (`hoverPickCore.ts` -
  a Cut director's viewport squashes a full-aspect scene into a rect, so the pointer is
  un-squashed into that scene's camera NDC; partition MASKS are not evaluated, the
  topmost full-frame layer wins). Ranking: real objects before full-frame planes (Text,
  Video, Film Stock cover every pixel), the front/invert passes before base, nearest within
  a pass. The glow is VisualScene's `hoverMaskTarget` + `hoverGlowMaterial`: the hovered
  roots are re-rendered alone on layer `HOVER_MASK_LAYER` into an alpha mask (their own
  materials - lights stay on layer 0, so they render unlit, which a mask does not mind),
  then a dilated edge is drawn additively after the final grade and invert overlay. Gated
  on `isExportPinned()` so it never reaches an export or a thumbnail capture. Hover state
  is written only when the hovered track CHANGES (UIStore.canvasHover), never per move.
- `ObjectRenderer.tsx` — one OCCURRENCE of one object: placement group → post-mover scale → its VisualCopy transform; `MaterialWrapper`/`TransformWrapper`/`ShaderWrapper` apply the effect chain inside (material innermost, closest to the meshes). Never resolves copy logic itself.
- `MaterialWrapper.tsx` — `material` effects: patches the target's own materials via `onBeforeCompile` so a generated surface travels WITH the mesh, and restores them on unmount/disable. See `effects/CLAUDE.md` for the contract and its limits.
- **`placementKey` in VisualScene IS the pass partition**, not a cache key: it builds one character per object (`'B'` base / `'F'` front / `'I'` final-invert) and the three `createPortal` blocks at the bottom filter on it. Both it and ObjectRenderer's full-frame branch resolve through `instruments/types.ts`'s `isFullFrameTrack` / `isOnTopTrack` — change one and you must change the other, or an object mounts in a pass its renderer isn't expecting.
- **A full-frame instrument in the front pass hides the whole scene behind it**, background included, even with a fully transparent texture — the front pass composites over the base and a viewport-filling plane covers every pixel of it. Long-standing, easy to mistake for a bug in the instrument. It is the main reason the Oscilloscope now defaults to an in-scene object instead of a pinned overlay. The mechanism (found 2026-07-30) is NOT the pass itself: `applyMaterialOpacity` resets `material.transparent` to false at full fade, so the plane draws opaque and REPLACES the frame. A material carrying `FORCE_TRANSPARENT_KEY` (see instruments/CLAUDE.md) keeps real alpha blending, and a full-frame plane then genuinely lets the scene through its transparent pixels (Flash Wall's Fill mode).
- `RenderGovernor.tsx` — paused = `frameloop='demand'`; invalidates exactly one frame on: any ProjectStore change, the debounced structural re-resolve (~80ms later), beat moves while paused, play→pause edge, canvas resize. The frameloop prop must stay a Canvas PROP (Canvas re-applies props and would clobber imperative setFrameloop).
- **Fast Preview** (`UIStore.previewQuality`: `final`/`auto`/`fast`/`fastest` — **`auto` is transport-driven**: full res paused, half while playing, resolved by `previewQualityScale(quality, isPlaying)` which is what callers read, never the raw `PREVIEW_QUALITY_SCALE` record; motion hides the drop and the paused frame is the one that gets scrutinised and captured — the `QUALITY <level>` chip next to the aspect select in App.tsx's TransportStrip; `PREVIEW_QUALITY_SCALE` maps each level to its linear resolution factor, `PREVIEW_QUALITIES` fixes the cycle order): VisualScene multiplies the factor into every offscreen target's size (scene/invert/filter targets, composite, bloom) so a frame costs scale² of the full fragment work; the final grade pass upscales (all targets are LinearFilter) and the on-screen buffer keeps full DPR. The scale stands down while the frame driver is pinned (`isExportPinned` in core/export/frameDriver.ts) — export and preview captures always render full-size. **`useRenderTargetScale()` is the one place that number is derived**; VisualScene and ShaderWrapper both read it, so a per-object shader rig shrinks with the compositor's targets. ShaderWrapper also OWNS only one target per copy (its final output) and borrows source + ping-pong intermediates from `shaderScratchPool.ts`, a module pool shared by every wrapper — a chain runs to completion inside one useFrame, so only the last pass's texture has to outlive it (a 4×4 grid of shaded copies went from 48 full-canvas targets to 16 + 3). The FXAA `resolution` uniform must track the SCALED composite size (texel steps sample that target); the backdrop-gradient `resolution` deliberately stays the CSS size (its shader math is ratio-only, invariant under uniform scaling).
- **Empty passes are SKIPPED** (2026-08-15): `passPresence` (derived from `placementKey`, so it is structural) says which scenes actually hold front / final-invert objects. Most hold neither, and the loop used to pay a depth clear + full pass (front) and a target switch + clear + render (invert) per scene per frame regardless, plus the invert compositor pass over the finished frame. Two rules if you touch it: the invert TARGET must still be transparent black when skipped, so a scene clears it once and latches `MountedScene.invertBlank` (reset on `setSize` — a resize discards contents); and the compositor's invert overlay is skipped only when NO composited layer's scene has invert objects.
- `DevRenderStats.tsx` — dev-only draws/triangles/programs readout, the measuring stick for renderer work. Hidden by default; `window.__cabinRenderStats(true)` toggles it (localStorage-backed). It owns `gl.info`: `autoReset = false` plus ONE manual `info.reset()` per frame at useFrame priority 1000 (after VisualScene's 100), because three resets the counters after every `render()` call and VisualScene issues a dozen per frame — with autoReset on you would read only the last pass.
- `ExportDriver.tsx` — bridges the export engine to the canvas.

## Inspector & the rest

- `TrackEditor.tsx` — the detail/inspector panel: dispatches per track type to registered settings UIs (`userInterfaceRenderers/`), effect chains, envelope/automation config, scene settings (`SceneSettingsPanel.tsx`). The rail carries a CONDITIONAL third tab, **Targets** (`targetChannels`), holding both things a device can point at: the #tag/branch/track OBJECT routing (global movers and Crop — it used to sit inline on the Instrument tab) and the COPY console (`CopyTargetsUserInterface`, for any mover/splitter row). A plain instrument has neither and keeps the two-tab rail; an effect that removes the open tab needs the bounce-back effect beside the other two, or the body renders with no tab lit. Identity is the **masthead** above the tab rail — `panelIdentity()` resolves name + kind (tooltip) + color; the name renders at 22px display serif on the panel surface, and the color lights the ACTIVE tab. The rail is a `@container` that drops to short tab labels under 300px. Two things here are load-bearing: the name row draws **no rule of its own** (size separates it; the rail's hairline closes the header — two stacked rules read as two toolbars), and **`leading-[1.3]`** on that serif, because `truncate` is `overflow:hidden` so a tighter line-height clips every descender and looks like a broken font. Louder identity (the header on its own raised/recessed surface, tinted with the track color) was built and rejected as too much for a panel this size — `docs/instrument-panel-design-guide.md` records the two traps waiting if it returns. Early (rail-only) design options are at `/dev/panel-header-lab`; the masthead was chosen by building the finalists into the live editor behind a temporary switcher, because the height cost only shows up against a real pane.
- `LeftSidebar.tsx` — the library. **`ALL_OBJECT_INSTRUMENTS` is the curated instrument picker** — new instruments must be added here as well as the registry. The instruments tab is a Logic-style drill-down (`FolderBrowser`): folders are plain rows you click into, a sticky back row returns one level, and cards appear only at the level that holds them. `SCENE_FOLDERS` is the scene tree (Main gets its composition instruments — the `'director'` LIBRARY kind, which survives the track-type retirement — at the root via `rootItems`); folders claim items from the item arrays BY ID, and an unclaimed id renders NOWHERE (the Unsorted catch-all folder was removed 2026-08-15) — filing a new item into a folder is part of adding it. **A new mover lands in Motion automatically** (Motion is "every mover minus the ones Impact claims"), so filing one is usually a one-line edit to `IMPULSE_IDS`/`RUMBLE_IDS` or nothing at all. Extras folders live INSIDE the folder they belong to (Motion → Extras), not at the root. Empty folders hide their row. **Motion → Extras is populated from the definitions' own `legacy` flag** (`LEGACY_MOVER_IDS`, derived from the registry), not a hand-kept id list — the same flag drops those definitions from `TrackContextMenu`'s "Add mover / colorizer / splitter track" lists, which have no Extras drawer to demote them into. See `core/visualCopies/CLAUDE.md`. Drag source: `useLibraryDrag`.
  **The library header's tab row is a two-step `@container` ladder** (`LIBRARY_TABS` + the three
  `*Mark` glyph components at the bottom of the file). The tabs are icon + label; the marks are
  hand-drawn rather than lucide because the old set (Shapes / Repeat / LayoutTemplate) had two
  glyphs sharing one silhouette at 13px, so Instruments and Templates could only be told apart by
  hovering. Instruments and Loops are duotone — a plane at ~0.38–0.55 with the load-bearing part
  lit at full — and **a plane much below 0.38 disappears entirely**, because the row rests at
  `--text-muted` over `--bg-shell`; that opacity is the first thing to check if the marks ever look
  hollow. Two traps in the width: the threshold is **content-box**, because that is what a
  container query sizes against, so it reads 20px *lower* than the layout width it fires at
  (`@[310px]` → ~330px of sidebar); and it is **measured in Hanken Grotesk**, not guessed — the
  pills lay out at 320px alongside the caption. **Collapse order is load-bearing: the labels go
  first and LIBRARY only yields after them.** An earlier two-step ladder dropped the caption in the
  band where labelled tabs fit alone; it reads fine still, but the caption vanishing while the tabs
  are fully dressed looks like a bug mid-drag (rejected in review 2026-08-13). A 1280-wide window at
  the 25% default lands at 320px, just under the threshold, so that size shows icons.
  Re-measure when the UI font, a tab name, or the tab count changes.
  The caption also carries `min-w-0 truncate` and the buttons
  `flex-shrink-0`, so at the panel's 8% minimum the caption ellipsizes instead of the 24px hit
  targets collapsing to ~9px. Loop ROWS still draw lucide `Repeat` in emerald — deliberately not
  yet unified with the tab's block mark.

  **Switcher** is the current card for a CONTAINER (`'switcher'` LibraryKind, filed in Utility): `useLibraryDrag.makeTrack` builds a `switcher` track that lands EMPTY, and double-click WRAPS the selected track rather than converting it — converting would destroy the very track you meant to rack. Its preview has no object of its own, so it previews as what it does: three solids taking the frame in turn, driven by the real `liveChildrenAt` on real notes (Latch, because a Gate loop would spend a third of its time empty and read as broken). Same three lists as below must agree, plus both preview dispatches.

  **A library card need not be an instrument.** Movers, splitters and colorizers already are cards for things that aren't, and **Word Formation** (`'wordFormation'` LibraryKind, filed in Utility right under Text Display) is the first card for a CHILD LANE: `useLibraryDrag.makeTrack` builds a `wordFormation` track, and the drag REFUSES any drop whose parent's instrument doesn't declare `seatsWords`, so the indicator never promises a landing that would leave an inert row on a cube. Double-click adds the lane UNDER the selected text track instead of converting it (converting would delete the very text the formation arranges), resolving a selected lane to its parent first. Three lists must agree or it half-works: `SCENE_ITEM_POOL` (folder `pick()` reads it), `ALL_LIBRARY_ITEMS` (what the CLIP CAPTURE harness enumerates — declare the items above it, or the const is in TDZ at module init), and the two preview dispatches (`InstrumentHoverPreview`'s layer and `InstrumentPreviewCapture`'s canvas). Miss the capture dispatch and `canPreview` still admits the id, so the harness captures a BLANK clip and uploads it — worse than having no clip, since the manifest then hides the live preview.
  **Object instruments file differently from scene items.** `SCENE_ITEM_POOL` is built from `OBJECT_INSTRUMENTS` (the `CORE_OBJECT_IDS` five), not `ALL_OBJECT_INSTRUMENTS`, so a new entry in `ALL_OBJECT_INSTRUMENTS` lands in `EXTRA_INSTRUMENTS`, the collapsed "back catalog" folder at the very bottom, which is where users do not look. Filing one into its own folder means subtracting its id from Extras as well as adding the folder (see `INSTRUMENT_FOLDER_IDS`); `pick()` reads the pool, so it cannot select a non-core object — filter `ALL_OBJECT_INSTRUMENTS` directly.
- **R3F previews wear the "Neon Stage" look** (`InstrumentHoverPreview.tsx`, picked from a tint mock 2026-08-15): `PREVIEW_COLOR_REMAP` swaps dusty default instrument colors for electric equivalents (preview-only — real tracks keep their stored defaults), and `PreviewBackdrop` paints a same-hue radial glow as a CanvasTexture scene background (a flat `<color>` can't hold a gradient) in both the hover popup and the baked clips. The foreground key comes from `previewForegroundHex` — first `color` param, stored value for track rows, preview-cube cyan for movers/splitters. The hue math is hand-rolled **sRGB** HSL on purpose: three's `Color.getHSL/setHSL` operate in the LINEAR working space, so a lightness chosen against an on-screen hex renders far lighter than intended — a trap for any future "just darken this color" helper.
- Library previews (`InstrumentHoverPreview.tsx` + `InstrumentPreviewCapture.tsx`): cards are **clip-first** — they play `<id>.mp4` from the public `instrument-previews` bucket, and the bucket's `manifest.json` is the EXISTENCE record; an id absent from it falls back to the live R3F preview (so a new mover previews before its capture runs, and a stale clip means the card ignores your code until recaptured). The hover popup is always live. Movers default to ONE offset cube + wireframe ghost, which reads as broken for anything that choreographs a whole arrangement (a physics blast flings the lone cube off-frame in a frame or two) — give those an entry in `COMPOUND_MOVER_PREVIEWS`: a `gridSeeds`/`ringSeeds` field of small cubes, notes in the mover's own pitch vocabulary, a `label`, and **preview-tamed `settings`** (defaults are tuned for scene-scale distances, not a 2.5-unit popup grid). Regenerate clips with `npm run previews:instruments -- <id>` (uploads to Supabase). To VERIFY a preview without uploading — and note the embedded Browser pane cannot show it live (`document.hidden` ⇒ no rAF ⇒ live canvases freeze and fresh ones never init) — run a local Playwright script against `/dev/instrument-previews` calling `window.__captureInstrumentPreview(id)` (deterministic stepped clock, works hidden), save the returned base64 MP4, and read it as an ffmpeg contact sheet (`select=not(mod(n\,8)),tile=10x3`). Captured frame `n` renders beat `(2·n/30 + 1) % 16` — the +1 is `START_OFFSET_BEATS`, so frame 0 is beat 1, not beat 0.
- **Dialogs share one shell: `EditorDialog.tsx`** (Export, its signup gate, Save to cloud). Portal + scrim + `#0f1118` card at radius 14 + a 30px close square, with the Radix dialog motion (fade + zoom-95, 200ms in / 150ms out) — mount it under an `<AnimatePresence>` or the exit is cut. Two LOOKS, and they are not interchangeable: `variant="chrome"` is a tool window (Archivo-700 / 14px / uppercase at 0.12em, asymmetric padding — Export) and `variant="prompt"` is a card that asks you something (UI sans, 15px semibold, sentence case, even 26px — every signup surface). Both are byte-for-byte what shipped before the extraction; don't "unify" them. Three more props exist only for NESTING (the gate floats over the export settings): a module-level stack means **only the topmost dialog handles the keyboard** — portaled siblings don't `contain()` each other, so without it an outer dialog swallows Space/Enter typed into an inner one and Escape closes both — plus `claimModal={false}` so an inner dialog's unmount can't clear `modalOpen` while the outer is still up. (`animated={false}` exists for a surface that must appear with no motion, and nothing passes it now — the export gate did, and popping in on one frame read as a glitch beside the panel it floats over, so it takes the shell's motion under its own `AnimatePresence` like every other dialog.) `SignupCard.tsx` is the shared signup body (email + Google + log-in link, `stashAnonWork` on open); its `page` prop keys BOTH analytics and the GSI container id, because Google renders its button into a real DOM node and two mounted cards would fight over one id. That gate makes the `/projects` guest-cap prompt unreachable; it stays in the tree so deleting the gate restores it.
